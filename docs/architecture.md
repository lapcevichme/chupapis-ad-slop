# Архитектура бэкенда

Бэкенд построен по Monolith-backend-template (MIT, уведомление в `backend/LICENSE.template`):
FastAPI + async SQLAlchemy + PostgreSQL + Redis + S3-совместимое хранилище. Сохранены кампании,
агент и внешний контракт кейса; заголовки `X-User`/`X-Role` заменены настоящей JWT-авторизацией.

```text
HTTP → api → service → domain
               ↓
            db / infra
```

| Слой | Ответственность |
|---|---|
| `app/main.py`, `bootstrap.py` | Фабрика, lifespan и сборка зависимостей |
| `api/` | HTTP, DI, схемы запросов, ошибки, SSE-кодирование, OpenAPI и request id |
| `contracts/` | Общие Pydantic-схемы для HTTP и tools; не зависят от транспорта |
| `service/` | Сценарии кампаний, креативов, справочников, чата, авторизации, медиа; outbox |
| `domain/` | Правила, роли и права, enum, переходы состояний, dataclass-представления |
| `db/` | ORM-модели, репозитории, UoW, сид |
| `infra/` | S3, rate limit, уведомления, checkpointer, LLM/изображения, граф и tools, CBRO-заглушка |
| `core/` | Настройки, каталог ошибок, безопасность (пароли, токены), логирование |

Домен не импортирует FastAPI, SQLAlchemy или Pydantic. Сервисы не импортируют API/FastAPI. API не
строит SQL и не возвращает ORM: между сервисом и HTTP стоят доменные dataclass и явное `from_domain`.
Границы проверяет `tests/test_architecture.py`.

## База данных

Одна PostgreSQL 17. Схема создаётся одной начальной миграцией `0001` (старые SQLite-ревизии сведены в неё),
дальше только новые ревизии. Решения, ради которых схема устроена именно так:

- **Типы.** Перечисления — нативные enum Postgres (`campaign_state`, `user_role`, `audit_action` и др.).
  Все моменты времени — `timestamptz`. JSON баннеров, контента, аудита и макетов — `jsonb`. Начало и конец
  показа — `start_at`/`end_at` в UTC; API по-прежнему отдаёт дату и время раздельно.
- **Целостность в БД, а не только в сервисах.** `CHECK`: конец позже начала, вес ≥ 0, CTR от 0 до 100,
  остановленная или архивная кампания не опубликована. Креатив ссылается на баннер и контент составным
  внешним ключом `(campaign_id, id)`, поэтому связать баннер чужой кампании нельзя. Активный диалог на пару
  «пользователь + кампания» один: частичный уникальный индекс `WHERE archived_at IS NULL`.
- **Пользователи.** `users` с уникальной почтой и именем без учёта регистра. Автор кампании и автор записи
  аудита — внешние ключи на `users`; API по-прежнему отдаёт `author` строкой (имя пользователя).
- **Справочники** — таблицы с ключами из кейса. Каналы типа баннера — таблица `banner_type_channels`, а не JSON.
- **Идентификаторы.** Кампании, баннеры, контент, креативы — `integer identity`: числа 101–115 из кейса сохранены,
  последовательности сдвигаются после сида. Остальное — UUID.
- **Аудит** переживает удаление кампании: у `audit_log.campaign_id` нет внешнего ключа намеренно.
- **Медиа.** `media_objects` (ключ, тип, размер, владелец) и `studio_documents`; сами байты в S3. Квота загрузок
  считается запросом к БД, а не обходом каталога.
- **Имена ограничений** детерминированы (`naming_convention`), поэтому downgrade удаляет их по имени.
- **Таблицы чекпоинтов LangGraph** живут в той же БД, но ими управляет библиотека
  (`python -m app.cli setup-checkpointer`); Alembic их игнорирует (`include_object` в `alembic/env.py`).

## Жизненный цикл и транзакции

`create_app(settings)` ничего не открывает при импорте. Lifespan владеет `Database`, Redis, S3, пулом
соединений checkpointer и сервисом чата и закрывает их при завершении. Настройки передаются явно: два
приложения могут работать с разными БД.

Каждый запрос получает один UoW через `Depends(scope="function")`. Сервисы меняют объект и вызывают `flush`;
владелец UoW коммитит **до ответа** и откатывает при ошибке. Кампания, аудит и событие outbox пишутся в одной
транзакции. Исключение — ошибка с `keep_changes` (повторное использование refresh-токена): сессия отзывается и
запрос всё равно отвечает 401. Миграции, таблицы чекпоинтов и сид делает отдельный шаг (`migrate` в Compose),
а не каждая реплика.

## Авторизация

Access-токен — JWT RS256 на 15 минут. Refresh-токен непрозрачный, хранится в `auth_sessions` хэшем и
ротируется при каждом обновлении; повторное предъявление старого токена убивает сессию. Веб-клиент держит
refresh в httpOnly-cookie (путь `/api/auth`, по пути прокси фронтенда) и повторяет CSRF-токен в заголовке.
Мобильный получает его в теле. Бан, смена роли и «выйти везде» поднимают `users.auth_version`, и выданные
токены умирают на следующем запросе. Пароли — argon2id. Регистрация, вход и обновление ограничены по IP
через Redis.

Роли — код (`domain/users.py`), а не таблицы: `campaignManager`, `campaignModerator`, `admin`; каждая — набор
прав. Эндпоинты проверяют права. Одобрять и возвращать кампании может только модератор, даже админ.

## Агент и границы I/O

`service/chat.py` управляет диалогом; граф и инструменты живут в `infra/agent/`. Состояние графа лежит в
PostgreSQL (`AsyncPostgresSaver`), связь пользователь + кампания — в `chat_sessions`.

Агент читает и пишет кампании через `infra/campaigns_api.py` по HTTP **с access-токеном того пользователя,
от чьего имени идёт ход**. Токен передаётся в конфиге графа под ключом `__api_token`: LangGraph не пишет ключи
с `__` в метаданные чекпоинта, поэтому токен не попадает в БД. На запись агент получает только `propose_*`;
подтверждённый пакет исполняет контролируемый узел. LLM, изображения и HTTP не держат транзакцию кампании.
Пакет из нескольких запросов **не** является одной транзакцией; поведение частичного исполнения — отдельный риск.

## Побочные эффекты: outbox и воркер

Отправка на модерацию, решение модератора и запуск кампании пишут событие в `outbox_events` в той же транзакции.
Отдельный процесс `python -m app.worker` забирает события (`FOR UPDATE SKIP LOCKED`), шлёт уведомление
(лог или Telegram) и на запуске выгружает кампанию в ЦБРО (пока заглушка). Доставка at-least-once, повтор с
экспоненциальной паузой, после лимита событие помечается `dead`. Воркер же чистит просроченные сессии.

## Медиа

Файлы лежат в закрытом S3-бакете. API отдаёт их по `GET /media/{ключ}` без авторизации (ссылки вставляются в
`<img>` и в JSON баннера) с вечным кешем: имена случайные и неизменные. Загрузка идёт через API (клиент сам
сжимает фото), формат определяется по байтам. Картинки и SVG от агента сохраняет `MediaStore`.
