# Архитектурная база и план переработки

**Статус:** описание существующих границ и ориентир для следующего этапа. Шаблоны пользователя ещё не предоставлены. Само наличие кода не фиксирует будущую архитектуру; перестройка не начата.

## Требования, которые переживают замену реализации

По [task.md §§6.2, 10.8](../case/Кейс1/task.md#sec-6-2): агент использует инструменты с JSON-схемами, читает справочники, проверяет JSON до API, запрашивает подтверждение записи, сохраняет многошаговый контекст и допускает замену модели. Сервер проверяет роли, жизненный цикл и ведёт аудит. Возможность подключения настоящего API нужно доказать границей транспорта, а не обещанием в презентации.

```text
React UI ── API кампаний ── FastAPI ── домен / SQLite / аудит
    │                          ↑
    └── chat + SSE ── граф ── HTTP-клиент кампаний
                        │
                  абстракция LLM
                        │
             чтение / предложение изменений
                        ↓
               подтверждение человеком
                        ↓
              детерминированное выполнение
```

Это текущая схема проекта, совместимая с требованиями. HTTP-граница агента, Pydantic-схемы и подтверждение в графе — полезные кандидаты на сохранение. Задание не предписывает конкретно FastAPI, LangGraph, React или SSE: это выбор команды.

## Текущий стек

| Слой | Что сейчас | Где смотреть |
|---|---|---|
| API | Python 3.13, FastAPI, Pydantic | `backend/pyproject.toml`, `app/routers/`, `app/schemas/` |
| Домен и хранение | SQLAlchemy 2, SQLite, Alembic | `backend/app/domain/`, `models.py`, `alembic/` |
| Агент | LangGraph, interrupt, SQLite checkpointer; адаптер OpenAI-совместимых API | `backend/app/agent/`, `uv.lock` |
| UI | React 19, Vite, TypeScript, TanStack Query, Tailwind, shadcn/Base UI | `frontend/package.json`, `src/` |
| Контракт | FastAPI OpenAPI → сгенерированные TS-типы; Pydantic → схемы tools | `frontend/openapi.json`, `src/types/`, `docs/tools.json` |
| Запуск | Docker Compose, один backend + frontend, постоянный volume данных | `docker-compose.yml` |

Не добавляем зависимости и сервисы без конкретной необходимости. Redis/очереди, второй API-сервис и полноценная production-авторизация для основного демо не нужны. Если выбранный шаблон меняет слой, фиксируем решение и сохраняем контракты либо меняем все стороны вместе.

## Точки интеграции

- `/api/*` — клиентский префикс Vite; прокси снимает `/api`. На сервере `/campaigns`, `/chat`, `/media`. `API_PROXY_TARGET` задаёт адрес backend; `CAMPAIGNS_API_URL` — адрес API для агента.
- `frontend/src/api/` — единый доступ компонентов к данным; текущий пользователь добавляет `X-User`/`X-Role`.
- [chat-api.md](ours/chat-api.md) — **действующий унаследованный контракт**, а не список нерешённых вопросов. SSE читается через fetch; схемы событий включены в OpenAPI. При переработке согласованно меняются сервер, клиент и типы.
- Пишущему API-вызову соответствует `propose_*`; выполнение происходит после `interrupt()` в графе. Схемы генерируются из Pydantic; не создаём параллельную ручную JSON Schema.
- Checkpointer хранит диалог и неподтверждённые операции; таблица `chat_sessions` связывает пользователя и кампанию с диалогом. Сессии менеджера и модератора разделены.
- Медиа — отдельная необязательная возможность. Недоступность генератора не должна ломать JSON-баннер и отправку на модерацию.

## Риски, которые необходимо проверить при переработке

1. **Частичная запись пакета.** Подтверждение может содержать несколько HTTP-запросов; это не общая транзакция. Сбой на середине требует правдивого состояния и безопасного продолжения. Не обещать атомарность или идемпотентность всех операций без проверки.
2. **Конкурирующие правки.** Модератор и менеджер работают с одной кампанией в разных чатах. Перед предложением действия нужно получить актуальное состояние, при записи повторить серверную проверку.
3. **Черновик и факт.** Неподтверждённые данные не должны выглядеть сохранёнными. Финальный превью перед модерацией должно соответствовать данным API.
4. **Повтор после сбоя.** Повтор SSE/подтверждения не должен дублировать записи. Восстановление после рестарта и обрыва проверить отдельно от сценарной модели в памяти.
5. **Провайдер и промпт.** OpenAI-совместимый транспорт не доказывает поддержку любого провайдера. Отдельно проверить tool calling, схемы, тайм-ауты; названия и цены из старого README не считать исследованными.
6. **Совместимость с реальным API.** Локальные media URL, дополнительные коды ошибок и допущения клиента — явные расширения, а не незаметная часть задания.

Это список приёмки, не утверждение, что все перечисленные дефекты есть в текущем коде.

## Как сравнивать шаблоны

Когда будут пути, сначала изучить их инструкции и лицензию, способ запуска, настройки, API/БД, миграции, ошибки, логирование и frontend-примитивы. Составить таблицу «требование → старое решение → решение шаблона → перенос/перепись»; не копировать всё дерево поверх рабочего кода.

Порядок переноса: доменные схемы/инварианты и эталоны → API/аудит → инструменты и подтверждения → UI ключевого сценария → дополнительные медиа. Каждый самостоятельный рабочий фрагмент проверяется и коммитится. Контракт меняется одним коммитом с типами и инструментами.

Перед миграцией данных: проверить единственную Alembic head и актуальное состояние main; чужие правки не перезаписывать. SQLite-специфичные запросы не добавлять. Секреты остаются в `.env`, переменные описываются в `.env.example`.
