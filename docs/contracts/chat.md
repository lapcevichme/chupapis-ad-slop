# API чата: контракт фронта и агента

**Статус: действующий контракт.** API кампаний описан в §3 `case/Кейс1/task.md`, здесь — API между фронтом и агентом. Меняем контракт одним коммитом вместе с типами фронта и кодом агента.

> Контракт сохранён после переноса бэкенда. При переработке сверяться с [../architecture.md](../architecture.md) и фиксировать изменения в [../DECISIONS.md](../DECISIONS.md). Описанные здесь `/api/media/` и другие расширения реализации не становятся требованиями организаторов.

Исходные условия:

- Паспорт и превью принимают данные в форме `CampaignDetailsDto` из §3, типы лежат в `frontend/src/types/api.ts`.
- Vite проксирует `/api/*` на бэкенд, убирая префикс `/api`. Бэкенд отдаёт пути без префикса (`/campaigns`, `/chat`), адрес задаётся `API_PROXY_TARGET`, по умолчанию `http://localhost:8000`.
- Каждый запрос, в том числе в чат, содержит `X-User` и `X-Role`. Агент передаёт их дальше в API кампаний.

## Главный принцип: модель не пишет в API сама

У LLM есть только инструменты чтения и инструменты-предложения (`propose_*`). Пишущие вызовы API выполняет отдельный детерминированный узел графа LangGraph и только после того, как `interrupt()` получил подтверждение пользователя. Обойти подтверждение промптом нельзя.

Требование «инструмент на каждый вызов API» (§6.2) выполняется один к одному: на каждый GET есть инструмент чтения (`list_segments`, `get_campaign`…), на каждый пишущий вызов — `propose_*` с JSON-схемой тела этого вызова (`propose_create_campaign` → `POST /campaigns`, `propose_set_segments` → `PUT /campaigns/{id}/segments` и т. д.). Полная таблица соответствия — в `backend/README.md`.

## 1. Сообщение и поток ответа

`POST /chat/{sessionId}/messages`, тело `{"text": "...", "voice": false}`. `voice: true` включает правила голосового режима из `prompts/voice.md` (то же поле есть в ответе на карточку, повтор хода сохраняет прежний режим). Ответ — поток SSE, фронт читает его через `fetch`, а не через `EventSource`.

```text
message_delta          {text}                                  текст ассистента по кускам
step                   {id, label, status}                     шаг агента: "Ищу сегменты…"; status: running | done | failed
suggestions            {questions: [{header, question, multiSelect, options: [{label, value, description?}]}]}  опросник, например сегменты
confirmation_required  {id, title, operations, changes}        просим подтвердить запись (§2)
draft_updated          {draft, validation}                     текущий черновик для паспорта и превью (§3)
campaign_updated       {campaignId}                            запись прошла, фронт перечитывает кампанию
warning                {message, severity}                     предупреждение о спорном решении; severity: info | warning. Агент при этом не отказывается
error                  {code, message}                         сбой LLM или сети, не бизнес-ошибка (§7)
done                   {}                                      ответ закончен
```

Сырые аргументы инструментов в `step` не отдаём.

Опросник: к каждому вопросу фронт добавляет поле «Свой вариант». Если вопрос один и в нём выбирается один вариант, клик сразу отправляет `value`. Иначе пользователь отвечает на вопросы и отправляет всё одним сообщением: на один вопрос — сам ответ, на несколько — строки `header: ответ`; несколько выбранных вариантов идут через запятую.

В текстовом чате у каждого вопроса минимум два варианта. В голосовом режиме вопрос может быть без вариантов (человек отвечает своими словами) или с одним вариантом (решение, о котором договорились при обсуждении пункта); каждая тема — страница голосовой анкеты.

Каждое событие в потоке — строки `event: <тип>` и `data: <JSON>`. Схемы данных описаны Pydantic-моделями и лежат в `openapi.json` в `components.schemas` под именами `ChatEvent*` (`ChatEventMessageDelta`, `ChatEventStep` и т. д.), фронт генерирует типы из них.

## 2. Подтверждение записи

`POST /chat/{sessionId}/confirmations/{id}`, тело `{"approved": true}` или `{"approved": false, "comment": "..."}`. Ответ — тот же поток SSE, что у сообщения.

Содержимое `confirmation_required` — сводка для показа, а не тела запросов к API:

```json
{
  "id": "conf-3",
  "title": "Создать кампанию «Вклад 16%»",
  "operations": [
    {"kind": "create_campaign", "label": "Кампания «Вклад 16%»"},
    {"kind": "create_banner", "label": "Баннер STORY «Сторис: вклад 16%»"}
  ],
  "changes": [
    {"field": "startDate", "label": "Дата начала", "from": null, "to": "2026-11-05"}
  ]
}
```

- `kind`: `create_campaign`, `update_campaign`, `set_segments`, `create_banner`, `update_banner`, `delete_banner`, `create_content`, `update_content`, `delete_content`, `create_creative`, `update_creative`, `delete_creative`, `create_place`, `create_tag`, `to_moderation`, `approve`, `decline`, `activate`, `stop`, `delete_campaign`.
- Одно подтверждение на пакет записей одного шага, как в §9.
- Если пользователь пишет сообщение, не ответив на подтверждение, оно считается отклонённым, а текст сообщения уходит агенту как комментарий к правке.
- Проверка подтверждения — в графе, в узле выполнения записей.

## 3. Черновик до сохранения

Черновик живёт в состоянии сессии агента (checkpointer). В API он попадает только при первом подтверждении: `POST /campaigns` и дочерние сущности. После сохранения черновик — это кампания из API плюс ещё не подтверждённые правки.

`draft_updated` присылает черновик целиком:

```json
{
  "draft": { "...": "CampaignDetailsDto без id, state, published, author, lastEditAuthor" },
  "validation": {"errors": [{"code": "...", "message": "...", "field": "..."}], "warnings": ["..."]}
}
```

- `validation` — той же формы, что ответ `GET /campaigns/{id}/warnings`.
- id баннеров, контента и креативов до сохранения временные строковые: `"tmp-1"`. Уникальны в пределах черновика.
- Пока дизайн-агент стримит баннер, `draft_updated` приходит не чаще раза в 150 мс.
- Пока бриф собирается, любое поле `draft` может отсутствовать, паспорт показывает «Не задано».
- По `campaign_updated` фронт сбрасывает `draft` и `validation` и показывает кампанию из API. Если после записи остались неподтверждённые правки, бэкенд присылает новый `draft_updated` после `campaign_updated`.

## 4. Ручные правки в паспорте

Менеджер правит шапку, аудиторию, места и правила показа прямо в паспорте, кнопкой «Изменить» в блоке. Модератор форм не видит.

- **Сохранённая кампания.** Фронт сам вызывает API кампаний: `GET` → изменение → `PUT /campaigns/{id}` и `PUT /campaigns/{id}/segments`. Это действие человека, поэтому карточка подтверждения не нужна. Роли, переходы и аудит проверяет бэкенд как обычно. Следующий ход агента перечитает кампанию.
- **Несохранённый черновик.** Он живёт в сессии агента, поэтому фронт отправляет правку агенту сообщением, дальше она идёт через карточку подтверждения.
- Пока агент отвечает или ждёт ответа на карточку по сохранённой кампании, править нельзя.
- Тексты и оформление баннера и промо-экрана правятся только через агента.

## 5. Сессии

- `POST /chat` с телом `{"campaignId": 104}` или `{}` возвращает `{"sessionId": "..."}`. С `campaignId` возвращается диалог пары «кампания + `X-User`»: существующий, а если его нет — новый (§10). Без `campaignId` каждый вызов создаёт новый диалог.
- `GET /chat/{sessionId}` возвращает `{campaignId, messages, draft, validation, pendingConfirmation}`, где `messages: [{"role": "user" | "assistant", "text": "..."}]` без системных сообщений, шагов и вызовов инструментов, для восстановления после перезагрузки. `campaignId` — `number | null`: пока он есть, паспорт берёт `state` и `published` из `GET /campaigns/{id}`, а содержимое — из `draft`, где могут быть неподтверждённые правки.
- Сессия переживает перезапуск бэкенда: состояние хранит checkpointer LangGraph в отдельном файле `checkpoints.db` рядом с `adpilot.db` (путь задаёт `CHECKPOINT_DB`).

## 6. Роли в демо

Переключатель пользователя в шапке: `ivanov.p` (`campaignManager`) и `petrova.m` (`campaignModerator`). Роль проверяет только API кампаний; агент роль не проверяет, а объясняет полученный `ROLE_FORBIDDEN`.

## 7. Ошибки

- Ошибки бизнес-логики (400 от API, warnings) агент объясняет обычным текстом с предложением исправления.
- Событие `error` — только сбои LLM и сети. Фронт показывает кнопку «Повторить».
- «Повторить» — это `POST /chat/{sessionId}/retry` без тела, ответ тем же потоком SSE. Сообщение пользователя к этому моменту уже в истории, повтор продолжает ход агента с последней сохранённой точки графа и ничего не дублирует. Повторно отправлять то же сообщение не нужно.
- Сообщение сохраняется в истории только вместе с открытием потока: граф запускается после того, как ушёл ответ 200 с `text/event-stream`. Если `POST /messages` не дошёл до сервера или вернул ошибку без потока, сообщения в истории нет, и фронт отправляет исходный запрос ещё раз — задвоения не будет. Если поток открылся и потом пришёл `error`, повторяем через `/retry`. Единственный край: поток открылся на сервере, но заголовки не дошли до браузера — тогда повторная отправка задвоит сообщение; на демо в локальной сети это не случается.
- Повторный ответ на уже выполненное подтверждение ничего не пишет второй раз и работает как `retry`. `comment` в `POST /chat/{sessionId}/confirmations/{id}` необязателен.
- Отмены ответа нет. Тайм-аут на стороне фронта — 90 секунд **без единого события**, а не на весь ответ. Во время долгого шага (генерация баннера или картинки) бэкенд раз в 15 секунд присылает SSE-комментарий `: keep-alive`.
- Результат проверки: у сохранённой кампании `GET /campaigns/{id}/warnings`, у черновика — `validation` в `draft_updated`.

## 8. Картинки

- Генерация изображений — после сквозного сценария: растровый генератор, запасной вариант — SVG от LLM, на крайний случай — несколько своих файлов. Баннер без картинки валиден.
- Бэкенд раздаёт файлы по `/media/...`. В JSON баннера пишется относительная ссылка `/api/media/<файл>` (`MEDIA_BASE_URL=/api/media`), она идёт через тот же прокси Vite, фронту настройка не нужна. Валидатор `image.url` принимает `https://` или этот префикс. Для реального API такие ссылки при экспорте заменяются на https-адрес хранилища.

## 9. Инфраструктура и данные

- `backend/` и `docker-compose.yml` пишет бэкенд. `frontend/Dockerfile` проверяем при первой сборке compose.
- Недостающие моки: `segments`, `places`, `tags` лежат в `backend/seed/`; `topics`, `segment_types`, `lifecycle_transitions` восстанавливаем из `mock-data.md`; `validation_rules` собираем из кодов §2–4 `task.md`, оригинал просим у организаторов.
- Типы фронта генерируются из `openapi.json` в репо, файл обновляется скриптом бэкенда. Фронт собирается без запущенного бэкенда.

## 10. Отдельные чаты и история

Раньше менеджер и модератор писали в одну сессию, а связь кампании с сессией хранил только `localStorage`. Теперь у каждой пары «кампания + логин» один свой диалог, и хранит эту связь бэкенд.

Почему общий чат не подходит:

- Сообщение при неотвеченном подтверждении считается отказом (§2). Если модератор напишет «Одобряю», пока у менеджера висит подтверждение, пакет менеджера отклонится, а кампания не будет одобрена.
- Модератор видит карточку подтверждения менеджера и может её нажать.
- Агент модератора помнит разговор с менеджером, а `approve` должен оставаться решением человека.

Бэкенд (сделано):

- Хранит связь «`campaignId` + логин → `sessionId`». Логин берём из `X-User`.
- `POST /chat` с `campaignId` возвращает существующую сессию этой пары, новую создаёт, только если её нет.
- Диалог новой кампании начинается без `campaignId`. Связь записывается при создании кампании, то есть при первом `campaign_updated`.
- Кампания перечитывается из API в начале каждого хода и в `GET /chat/{sessionId}`. Без этого агент менеджера будет считать кампанию на модерации после того, как модератор решил её судьбу в своём чате.
- Связь хранится в таблице `chat_sessions` (`session_id`, `user_login`, `campaign_id`), состояние самого диалога — в checkpointer. Если `checkpoints.db` потерян, а связь осталась, `POST /chat` начинает диалог заново под тем же `sessionId`.
- Привязка к новой кампании происходит в конце хода, в котором она сохранилась, в том числе если следующий шаг хода упал.
- Если кампанию удалили, следующий ход это видит: `campaignId` в сессии становится `null`.

Фронт (сделано):

- При выборе кампании и смене пользователя открывает диалог этого пользователя через `POST /chat`. Без кампании смена пользователя начинает новый диалог.
- В `localStorage` хранит только id текущей сессии, для восстановления после перезагрузки.
- При `NEEDS_WORK` показывает комментарий модератора из журнала аудита в блоке «Ход кампании».

Чат модератора начинается пустым: справа паспорт и превью, над полем ввода плашка «Одобрить / Вернуть на правки». Повторная отправка после отклонения идёт в диалоге менеджера, как требует задание.

Несохранённый черновик к кампании не привязан: если до первого подтверждения уйти на другую кампанию, вернуться к нему через список нельзя. Для прототипа это допустимо.
