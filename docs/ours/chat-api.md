# API чата: открытые вопросы

**Статус: черновик, ничего не решено.** Это вопросы от фронта к тем, кто пишет агента и бэкенд. Предложения ниже — только отправная точка: если у вас есть вариант лучше, меняйте. Фронт начнёт писать чат, когда пункты 1–4 будут решены.

Как работать с файлом: под каждым вопросом запишите решение в строку **Решение:** и поправьте формат так, чтобы файл стал контрактом. Если вы агент, предложите решение и покажите его человеку, но не записывайте как принятое без его согласия.

## Зачем это нужно

API кампаний описан в §3 `docs/oragnisators/task.md`, а API между фронтом и агентом нигде не описан. От него зависит вся левая колонка экрана и то, откуда берут данные паспорт и превью.

Что уже есть на фронте (`frontend/`):

- Паспорт и превью принимают данные в форме `CampaignDetailsDto` из §3, типы лежат в `src/types/api.ts`.
- Сейчас данные идут из моков через `src/api/campaigns.ts`, и его легко переключить на `/api/...`.
- Vite проксирует `/api/*` на бэкенд, убирая префикс `/api`. Значит, бэкенд отдаёт пути как в §3 (`/campaigns`, `/segments`), адрес задаётся `API_PROXY_TARGET`, по умолчанию `http://localhost:8000`.

Требования задания, которые должен выдержать контракт:

- Любая запись только после явного подтверждения, перед отправкой показываем превью (§6.2).
- Черновик сохраняется между сообщениями (§6.2), диалог не теряет контекст (§10.10).
- 400 от API превращается в диалог с предложением исправлений (§6.2).
- Диалоги нужно уметь записывать и воспроизводить (§8).

## Обязательно до начала работы над чатом

### 1. Формат ответа ассистента

Предложение: `POST /chat/{sessionId}/messages` с телом `{"text": "..."}` и ответ потоком SSE с событиями:

```text
message_delta          {text}                                  текст ассистента по кускам
suggestions            {items: [{label, value}]}               кнопки-варианты, например сегменты
confirmation_required  {id, action, summary, payload}          просим подтвердить запись
draft_updated          {draft}                                 текущий черновик для паспорта и превью
campaign_updated       {campaignId}                            запись прошла, фронт перечитывает кампанию
error                  {code, message}                         агент не смог продолжить
done                   {}                                      ответ закончен
```

Вопросы:

- Устраивает ли SSE, или проще обычный JSON без потока? Поток выглядит лучше на демо, но JSON заметно проще и надёжнее. Для фронта подходят оба варианта. Если SSE, то он идёт по POST, поэтому фронт читает его через `fetch`, а не через `EventSource`.
- Что поддерживает выбранная модель? Если потокового режима с tool calling у неё нет или он ненадёжен, это решает вопрос. Целевая модель банка GigaChat, замена модели не должна ломать контракт (§10.8).
- Нужно ли показывать в чате шаги агента, например «ищу сегменты»? Жюри оценивает объяснимость. Тогда нужно ещё событие `tool_call`.

### 2. Подтверждение записи

Предложение: `POST /chat/{sessionId}/confirmations/{id}` с телом `{"approved": true}` или `{"approved": false, "comment": "..."}`, ответ в том же формате, что и у сообщения.

Вопросы:

- Что лежит в `payload`: тело запроса к API или готовая к показу сводка? Фронту удобнее сводка плюс изменения по полям.
- Одно подтверждение на весь пакет записей (кампания, баннер, контент, креатив) или по одному на каждый вызов API? В демо из §9 подтверждение одно на шаг, поэтому фронт предлагает пакетное.
- Что происходит, если пользователь пишет сообщение, не ответив на подтверждение? Предложение: подтверждение считается отклонённым, а сообщение идёт в агента как правка.
- Где проверяется, что запись подтверждена? Предложение: на стороне агента, в месте вызова инструмента, а не в промпте, чтобы модель не могла это обойти.

### 3. Черновик до сохранения

Превью надо показать до `POST /campaigns`, когда кампании в API ещё нет.

Предложение: `draft_updated` присылает черновик целиком в форме `CampaignDetailsDto`, только без серверных полей (`id`, `state`, `author`). Тогда компоненты паспорта и превью не придётся писать дважды.

Вопросы:

- Где живёт черновик: в сессии агента или сразу в API как `DRAFT`? Если сразу в API, то создание кампании потребует подтверждения ещё до первого превью.
- Что с id баннеров и контента до сохранения? Предложение: временные отрицательные или строковые id, фронту достаточно их уникальности внутри черновика.
- Черновик приходит целиком или как изменения? Целиком проще, а объём маленький.

### 4. Ручные правки в паспорте

В заявке обещано, что поля можно править руками, а агент видит эти правки. Это Should Have, сейчас паспорт только для чтения.

Предложение: правка отправляется в сессию `POST /chat/{sessionId}/draft` с изменёнными полями, а не сразу через `PUT` в API. Иначе черновики агента и формы разъедутся. Ответ агента на правку не обязателен.

Вопросы:

- Делаем ли это вообще до стоп-кодинга?
- Как правка попадает в контекст модели: как системное сообщение перед следующим ходом?
- Как быть с полями сохранённой кампании? Там PUT — полная замена объекта (§3), и правка меняет состояние (`APPROVED → DRAFT`, §2.3).
