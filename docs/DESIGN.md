# Дизайн рабочего интерфейса

**Статус: полный редизайн панели, выбор направления.** Пользователь просит переизобрести интерфейс. Макеты и ход выбора — [design/brief.md](../design/brief.md). Токены фиксируем после просмотра вариантов. Старый [«Изумруд»](ours/design.md) описывает только прежний фронтенд.

## Режим и основной сценарий

По Design Studio это **product UI**: рабочее место менеджера/модератора, где важны чтение результата, контроль изменений и отправка на модерацию. Отдельный промосайт сейчас не нужен. Продуктовая база — [PRODUCT.md](PRODUCT.md).

Меняем постоянную раскладку «чат + паспорт + телефон» на последовательное раскрытие результата. До генерации внимание на брифе; после — на кампании и креативах. Ассистент, параметры и история доступны по задаче. Перед модерацией — целостная проверка с понятным подтверждением. На телефоне один рабочий контекст за раз, с явным переключением зон.

## Что необходимо спроектировать

| Состояние | Что пользователь должен понимать |
|---|---|
| Новый бриф | Что описать и как начать; пример не заменяет свободный ввод |
| Уточнение | Какое решение нужно принять и откуда взяты варианты |
| Сборка | Какой шаг идёт; уже доступный результат остаётся читаемым |
| Предложенные изменения | Что ещё не сохранено; состав операции и разница до/после |
| Подтверждение | Какое конкретно действие произойдёт при согласии и как отказаться |
| Проверка | Ошибка или warning; причина, место и следующий шаг исправления |
| Модерация | Что отправлено, кто принимает решение; `ON_MODERATION` не значит «показывается» |
| Возврат | Комментарий модератора, предложенное исправление, повторная отправка |
| Работающая кампания с правками | Показ старой версии продолжается; предложенная версия отдельно |
| Сбой / восстановление | Что сохранилось и как продолжить без дублирования записей |

## Неподвижные требования

- Русский интерфейс, понятные деловые формулировки. Пользователь не обязан понимать JSON, LangGraph, внутренние очереди операций и tool calling.
- Статус, ошибка и опасное действие различимы текстом и формой, а не одним цветом. Клавиатурный фокус виден; уменьшение движения учитывается.
- Превью строится из JSON баннера/PROMO и отражает реально предложенные или сохранённые данные. Нельзя показывать красивый несвязанный макет.
- Тема рабочего интерфейса не перекрашивает креатив. Внутри превью используются цвета и текст самого баннера.
- Сырой HTML от LLM не исполняется. Картинки и длинные русские тексты имеют понятные состояния загрузки/ошибки.
- В кейсе нет проверяемого брендбука (§10.9). Не выдаём придуманную стилистику за официальный интерфейс Сбера.

## Следующий дизайн-этап

1. Сохранить API, SSE и доменные действия; новый интерфейс строить вокруг результата. Frontend-шаблон пользователем не предоставлен, ожидание его пути работу не блокирует.
2. Через **Design Studio** подготовить два разных визуальных направления с реальными полями и русским текстом; показать отрисованные варианты пользователю.
3. После выбора зафиксировать токены и ключевые состояния в этом файле; утвердить взаимодействие «уточнение → превью → подтверждение».
4. Реализовать один рабочий вертикальный срез и проверить скриншотами на согласованных ширинах, затем расширить остальные состояния.

Визуальные референсы, проверка доступности и скриншоты нового дизайна **ещё не сделаны**. Численные контрасты и оценки из старого документа не переносим на будущую палитру.
