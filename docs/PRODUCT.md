# Продукт AdPilot AI

**Статус:** переработка, 31 октября 2026. Бэкенд переносится отдельной сессией на Monolith-backend-template; здесь проектируем самостоятельный продукт с новым сценарием панели. Источник доменной модели — [task.md](../case/Кейс1/task.md); продуктовый фидбек — [пересказ чекпоинта](../mihlap-checkpoint-summmary.md), с оговорками об авторстве.

## Задача и пользователи

Менеджер банка превращает текстовый бриф в проверенную рекламную кампанию и отправляет её человеку на модерацию. Сегодня он заполняет несколько форм, ищет справочники и вручную собирает JSON креативов; самые дорогие по вниманию этапы — креативы, подбор параметров и исправления после модерации (`task.md` §§1, 10.1).

Основной пользователь — `campaignManager`. Второй — `campaignModerator`, который оценивает результат и одобряет либо возвращает с комментарием. Клиент банка видит баннер и PROMO-экран; он не пользователь нашей админки. Роли аналитика, юриста и руководителя из прежней концепции не создают отдельные обязательные рабочие места.

**Главное целевое действие:** отправить собранную кампанию в `ON_MODERATION`. Это ещё не публикация. `APPROVED` означает одобрение; только `activate` делает `published=true` (`task.md` §10.2).

## Сквозной сценарий

1. Менеджер вводит бриф. Агент читает актуальные справочники инструментами.
2. Агент показывает, как понял задачу; уточняет существенные неоднозначности. Предлагает реальные сегменты, места, тему и теги с объяснением.
3. Собирает шапку, аудиторию, баннер, PROMO и креатив. Пользователь видит черновик и превью результата для клиента.
4. Показывает точный состав записываемых изменений. После явного подтверждения сохраняет кампанию и связанные сущности.
5. Выполняет проверку. Ошибки объясняет и предлагает исправить; warnings устраняет либо объясняет пользователю.
6. Показывает актуальное превью и запрашивает отдельное подтверждение отправки. Результат — `ON_MODERATION` и объяснение следующего шага.
7. Для сценария исправления читает комментарий модератора из аудита, предлагает изменения и после подтверждения отправляет повторно в том же диалоге менеджера.

Шаги основаны на `task.md` §§6, 9, 10.2. Пакетное подтверждение создания соответствует образцу §9; агент не получает разрешение на будущие произвольные действия.

## Приоритеты

| Уровень | Что включаем | Основание |
|---|---|---|
| P0 | Бриф → сохранённая кампания с баннером, PROMO и креативом → превью → модерация; справочники, валидация, подтверждения, аудит | §§6.2–6.3, 9 |
| P1 | Подбор аудитории с объяснением, вес/initialCtr, исправление после decline, остановка, объяснение запретов и истории | §6.1 |
| Поставка | README, схемы tools, промпты; по возможности минимум три записанных/воспроизводимых диалога | §8 |
| P2 | Генерация изображений с запасным вариантом | §6.4; преимущество, не условие основного сценария |
| Только после основного | Версии/A-B, ОРД/ЕРИР, статистика, правило двух рук, copy/resume/archive | §6.4; не обещать в MVP без отдельного решения |

Не строим конструктор сегментов, расчёт пересечений или точного охвата, лимиты показов/частоты, событийные триггеры, реальную доставку в приложение, SSO. Вес не гарантирует число показов. Публикация в CBRO — успешная заглушка, не интеграция с банком (`task.md` §§5, 10.5–10.7).

## Критические продуктовые нюансы

- **Аудитория — OR.** Возраст плюс города означает объединение, а не «возраст в этих городах». Числа клиентов относятся к отдельным сегментам; суммировать их в точный уникальный охват нельзя. При неподходящей семантике объясняем ограничение и согласуем вариант. Разбиение на две кампании само по себе пересечение не создаёт.
- **Никаких выдуманных условий оффера.** Творческий текст допустим по поручению пользователя; ставки, гарантии, сроки и свойства продукта берём из брифа или уточнения. Валидная JSON-схема не доказывает правдивость текста.
- **Черновик и сохранённое различимы.** Превью неподтверждённых правок не означает, что они уже записаны. В UI должно быть видно, что именно уйдёт на модерацию.
- **Статус и показ различимы.** У живой кампании повторная модерация не останавливает показ старой версии. `STOPPED` в базовом MVP необратим.
- **Ошибки и warnings различимы.** Отсутствие креатива по API даёт warning, но обязательное продуктовое демо должно включать креатив и превью. Не вводим более строгий запрет в серверный контракт без решения.

## Критерии готовности и доказательства

| Проверка | Как доказываем |
|---|---|
| Из брифа получен результат | Живой диалог, GET собранной кампании, статус `ON_MODERATION` |
| Подтверждения работают | Отказ не пишет; согласие исполняет показанный пакет; повтор ответа не дублирует запись |
| Креатив валиден | До API применена схема; перед модерацией errors пусты, warnings объяснены |
| Источники реальны | Сегменты/места/enum получены инструментами, а не придуманы моделью |
| Цикл исправления | 104: комментарий из аудита → исправления → повторная модерация |
| Запреты объяснимы | Неподходящая роль/состояние дают понятный отказ, а не обход ограничения |
| Контекст сохраняется | Несколько сообщений, перезагрузка UI и перезапуск сервера проверены отдельно |
| Поставка воспроизводима | Чистый запуск, задокументированные переменные, схемы tools и промпты |

Матрица связывает требования с будущей приёмкой; факт выполнения отмечаем только в [STATUS.md](STATUS.md). Автотест со сценарной моделью не заменяет живую проверку LLM.

## Что измерять на демо

Время от брифа до модерации, число уточняющих ходов, долю принятых полей без ручной правки, ошибки перед отправкой и успешность исправления после отклонения. Это предлагаемые измерения по §10.10, **результаты пока не замерены**. Не переносим из заявки утверждения «70% времени» или «за минуту» как установленные факты.

## Текущий дизайн-этап

Пользователь прямо разрешил шаблон и поручил **переизобрести интерфейс**, а не обновить оформление трёх колонок. Выбраны оформление «Брифа» и ассистент справа. Новая React-панель начинается с фокусированного брифа, после генерации раскрывает кампанию и креативы. Мобильная работа обязательна для демонстрации по QR. Лендинг — возможный следующий этап, сейчас приоритет у панели. Контракты сохраняем, пока не принято отдельное согласованное изменение.
