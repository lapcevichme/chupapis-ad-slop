# AdPilot AI — правила работы

Хакатон {Sib}Код, кейс 1: AI-ассистент, который по текстовому брифу собирает рекламную кампанию и отправляет её на модерацию. Команда из трёх человек, все пишут параллельно в одном репо. **Стоп-кодинг: 1 ноября, 10:00.**

## Источники правды

При противоречии побеждает источник выше по списку:

1. `docs/oragnisators/task.md` — задание, доменная модель, API, FAQ.
2. `docs/oragnisators/mock-data.md` и `docs/oragnisators/mocks/` — данные и контракты.
3. `docs/oragnisators/case.md` — исходный тизер кейса.
4. `docs/ours/CONCEPT.md` — заявка на отбор. Устарела там, где расходится с заданием: сегменты только для чтения, нет лимитов показов и проверки пересечений, другие статусы.

Перед работой с доменом читай нужный раздел `task.md`, а не полагайся на память. Если мок упомянут, но файла нет, восстанавливай его из `mock-data.md`. Если данных не хватает, спроси человека, а не выдумывай.

## Приоритеты

Сначала сквозной сценарий из §9 `task.md`: бриф → кампания с креативом → превью → `ON_MODERATION`. Пока он не работает, остальное ждёт.

1. Обязательное (§6.3): чат, черновик, подбор сегментов и мест, баннер + контент + креатив с превью, валидация, модерация, аудит.
2. Сценарии §6.1 и артефакты §8: README, JSON-схемы инструментов, промпты, 3+ воспроизводимых диалога.
3. Дополнительное (§6.4), начиная с генерации изображений. Она не должна ломать основной сценарий, если модель недоступна.

Не делаем: конструктор сегментов, лимиты показов и частоты, проверку пересечений кампаний, реальную доставку в приложение, SSO.

## Стек

- **Бэкенд:** Python 3.13, FastAPI, Pydantic, uv.
- **БД:** SQLite, SQLAlchemy 2, Alembic. Без SQLite-специфичных запросов и типов: должен оставаться возможным переход на PostgreSQL.
- **Фронт:** React 19, Vite, TypeScript, TanStack Query, Tailwind, shadcn.
- **Запуск:** Docker Compose одной командой. Redis и очереди не поднимаем.

Новые зависимости и сервисы добавляем, только если без них никак.

## Структура

```text
backend/    FastAPI: API кампаний, домен, БД, миграции, агент
frontend/   React: чат слева, паспорт кампании и превью справа
docs/       задание и наши документы
```

```bash
docker compose up --build         # весь проект
cd backend && uv run pytest       # тесты
cd backend && uv run alembic upgrade head
cd frontend && npm install && npm run dev   # http://localhost:5173
cd frontend && npm run build && npm run lint
```

Фронтенд:

- `src/features/` — экраны и их компоненты, сейчас там `preview/`. `src/components/ui/` — компоненты shadcn, они правятся под наш дизайн (см. `docs/ours/design.md`).
- `App.tsx` пока временный стенд превью на копии моков из `src/fixtures/`. Заменяется экраном чата и паспорта; фикстуры нужны, потому что Docker-образ фронта не видит `docs/`.
- `src/types/creative.ts` — временные типы, написанные руками по §2.6–2.8. Когда появится OpenAPI, заменяем их сгенерированными; до этого новые типы API кладём туда же, а не по компонентам.
- Запросы идут на `/api/*`: Vite проксирует их на бэкенд без префикса `/api`, адрес задаёт `API_PROXY_TARGET` (по умолчанию `http://localhost:8000`).
- HTML из контента креатива не вставляем как разметку (`dangerouslySetInnerHTML` запрещён): текст приходит от LLM. Для `format: "html"` есть `parseRichText`, он понимает только `<b>`.
- Ссылки в моках ведут на несуществующий домен, поэтому заглушка вместо картинки на стенде — норма. Она появляется через 1–3 секунды, после ошибки DNS.
- `frontend/Dockerfile` ещё ни разу не собирался.

## Инварианты домена

Нарушение любого из них — провал демо (§10.10):

- **Human-in-the-loop.** Любое пишущее действие агента выполняется только после явного подтверждения пользователя. Перед отправкой на модерацию показываем превью.
- **Никаких догадок.** Неоднозначные даты, сегменты и другие значения уточняем вопросом.
- **Только реальные значения.** ID, коды и enum берём из справочников через инструменты. Создавать можно только места показа и теги, и только после подтверждения (§10.4). Сегменты, темы, типы баннеров и каналы только для чтения.
- **Валидация до API.** JSON баннера и контента проверяем по схемам §2.6–2.7 до отправки. Ошибки и warnings превращаем в понятное объяснение и предложение исправления.
- **Роли.** `approve` и `decline` — только `campaignModerator` и только по решению человека. `activate` — только из `APPROVED` и после подтверждения.
- **Жизненный цикл на бэкенде.** Переходы, `published` и проверка ролей живут на сервере (§2.3); роль проверяется раньше состояния. Агент их не обходит, а объясняет отказ.
- **Аудит.** Все пишущие операции и переходы бэкенд пишет в таблицу аудита (§3).
- **Только синтетика.** Никаких ПДн и реальных данных клиентов в промптах, логах и артефактах (§10.8).

Детали контракта, на которых легко ошибиться:

- В телах POST/PUT `topic`, `tags`, `places` передаются как `{value, label}`, в ответах GET — сырыми значениями.
- Каждый PUT — полная замена объекта: для частичной правки GET → изменение → PUT.
- Ошибки: 400 с `{"errors": [{code, message, field}]}`, для несуществующих сущностей 404 и `ENTITY_NOT_FOUND`.
- Каждый запрос содержит заголовки `X-User` и `X-Role`.
- Коды каналов регистрозависимы: `iOS`, `ANDROID`, `WEB`.
- Время в UTC.

## Архитектура

Жюри оценивает инженерию (§7), поэтому:

- **Инструменты:** один инструмент на каждый вызов API §3. JSON-схемы генерируются из Pydantic-моделей, руками не пишем и не дублируем.
- **LLM за абстракцией:** логика агента не зависит от провайдера, модель меняется конфигом. Целевая модель банка — GigaChat.
- **Промпты отдельно от кода:** в своих файлах, не строками внутри логики.
- **Агент ходит в API кампаний через HTTP-клиент**, а не напрямую в БД, а его адрес задаётся конфигом. Так заглушку можно заменить реальным бэкендом.
- **Состояние диалога и черновика сохраняется** между сообщениями и переживает перезапуск.
- **Контракт фронта и бэкенда — OpenAPI от FastAPI.** TS-типы генерируем из него, а не пишем руками.

## Дизайн

Тема «Изумруд», светлая и тёмная: токены, типографика и правила в `docs/ours/design.md`. Перед работой с UI прочитай его.

- Цвета только через токены, без хардкода в компонентах.
- Статус и опасное действие никогда не передаём только цветом: при дальтонизме они сливаются.
- Превью баннера рисуется по его JSON и от темы интерфейса не зависит.
- Переключатель тем делаем после того, как заработает сквозной сценарий.

## Параллельная работа

- Работаем в `main`: маленькие коммиты, `git pull --rebase` перед каждым пушем. Короткая ветка с PR — только для рискованных кусков.
- Коммить и пушить только по просьбе человека. Без force push в `main`.
- В индекс добавляй конкретные файлы, а не `git add .`: рядом могут быть чужие незакоммиченные правки. Чужие правки не откатывай и не переформатируй.
- Сообщения коммитов: `feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`. Без строки `Co-Authored-By`.
- Изменение контракта API — один коммит вместе с обновлением типов фронта и инструментов агента.
- **Alembic:** перед созданием миграции подтяни `main`, у `alembic heads` должна быть одна голова. При конфликте пересоздай свою миграцию поверх чужой. Для SQLite включён `render_as_batch=True`.
- Секреты только в `.env`, он не коммитится; все переменные перечислены в `.env.example`.

## Как работать агенту

- Меняй только то, что нужно для задачи: без рефакторинга «заодно» и абстракций про запас.
- Перед словом «готово» запусти код и проверь результат. Если что-то не проверено или не работает, так и скажи.
- Тесты пишем там, где поломка убьёт демо: валидация, жизненный цикл, роли, инструменты агента, эталонные диалоги. На UI тесты не пишем.
- Для проверки используй кампании из моков: 101 и 108 — черновики для ошибок валидации, 103 — минимальный payload, 104 — цикл исправления после `decline` (§6.2, §10.3).
- Стиль и язык: код и идентификаторы на английском, пользовательские тексты и документация на русском.
